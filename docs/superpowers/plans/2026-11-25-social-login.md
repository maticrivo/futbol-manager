# Social Login with Auth.js Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace magic-link email auth with Google/Facebook sign-in on Auth.js tables, keep the pending-approval flow, and support admin and self-service account linking.

**Architecture:** Auth.js v5 with the Drizzle adapter and database sessions. Auth.js's `user`, `account`, and `session` tables are canonical; `user` is extended with the app's role, status, phone, nickname, locale, and timestamps. All member foreign keys become text UUIDs. Unknown provider emails create `pending` users.

**Tech Stack:** Next.js 16.4.6, React 19, TypeScript, Auth.js v5 (`next-auth@5.0.0-beta.30`), `@auth/drizzle-adapter@1.11.0`, Drizzle ORM 0.45, PostgreSQL 17 / Neon, Vitest.

**Spec:** `docs/superpowers/specs/2026-11-25-social-login-design.md`

## Global Constraints

- Use the Auth.js default PostgreSQL table and column names: `user`, `account`, `session`; `user.id` is a text UUID generated by `crypto.randomUUID()`.
- Pin `next-auth@5.0.0-beta.30` and `@auth/drizzle-adapter@1.11.0` so both resolve `@auth/core@0.41.0`. Do not install `next-auth@latest` (v4).
- Extend `user` with `role` (enum, default `member`), `status` (enum, default `pending`), `phone`, `nickname`, `locale` (default `en`), `created_at`, and `updated_at`.
- Every existing member foreign key becomes `text` and references `user.id`. Keep the `member_id` column names and the domain word "member" in app code.
- New social users are `pending`. Admins approve them. `pending` users can sign in and edit their profile but cannot use match, queue, or billing pages. `disabled` users cannot sign in and existing sessions must resolve to no member.
- `user.email` is read-only in the app after creation. Do not expose email editing in profile or admin forms, and reject a differing email patch.
- Different provider emails are different identities. Do not auto-link by name or avatar. Admin linking is limited to `pending` duplicates. Self-service linking attaches the provider to the currently signed-in user.
- Delete magic links entirely: no Resend, no login tokens, no `/login/[token]`, no invite/regenerate UI.
- Database sessions last 365 days: `maxAge: 365 * 24 * 60 * 60`.
- All user-facing copy must be added to `messages/en.json`, `messages/es.json`, and `messages/he.json`.
- Read `node_modules/next/dist/docs/` for the current Next 16 route-handler, `searchParams`, and server-action conventions before Task 4.
- Tasks 1–5 are one migration window. The full suite is expected to be red until Task 5; each task still ends with its own targeted test or verification.
- The database is reset, not migrated from existing rows. Local and deployment databases must be explicitly wiped before applying the new baseline.
- Execute in an isolated git worktree created by `superpowers:using-git-worktrees`. The current checkout has unrelated uncommitted work (match deletion, countdown, UI, messages); do not stage or commit it with this feature.

## Review Focus

These are the conditions most likely to break silently. Each has a test in the task that owns the code.

1. **A provider profile without an email** (Facebook phone-only account) must not create a user or session; it must land on `/login?error=email-missing`. Task 2.
2. **A disabled user with an otherwise valid Auth.js session** must be treated as signed out by guards and API routes. Task 4.
3. **A second provider with a different email** must create a pending duplicate, not silently attach to the existing member; admin linking must move the account and delete the pending row in one transaction. Task 6.
4. **A self-service link attempt for an account already attached elsewhere** must not steal it; the member must see `OAuthAccountNotLinked` guidance with a way back to the profile. Task 7.
5. **The destructive reset** must remove both `public` and Drizzle's `drizzle` schema, apply the new baseline, and keep restrictive member FKs so a user with history cannot be deleted accidentally. Task 1 and Task 8.
6. **Admin linking is pending-only and targets active members**; an active user with history must never be merge-deleted. Task 6.
